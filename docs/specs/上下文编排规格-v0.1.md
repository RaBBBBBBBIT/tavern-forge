# 上下文编排规格

- 版本：0.1
- 日期：2026-09-23
- 状态：v0.1 规格；上下文边界、预算和检索方案已确定。
- 依赖：[叙事运行时规格](./叙事运行时规格-v0.1.md)、[记忆与上下文材料规格](./记忆与上下文材料规格-v0.1.md)、[接口契约规格](./接口契约规格-v0.1.md)、[数据模型规格](./数据模型规格-v0.1.md)。
- 范围：上下文材料的收集、过滤、编译、预算、交付和泄漏检查。
- 非范围：具体模型提示词、数据库 DDL；插件完整 API 见《插件与扩展接口规格》。

本文只回答一个问题：**在某个执行阶段，模型到底应该看到什么。**

事件、公开状态、角色记忆、摘要和 Worldbook 的定义见《记忆与上下文材料规格》；Turn、Beat、Director、Actor、Chronicler 和提交边界见《叙事运行时规格》。本文不重新定义这些对象。

## 1. 编排目标和硬约束

上下文不是一段固定 Prompt，而是根据执行阶段生成的 `ContextSnapshot`。默认编排流程如下：

```text
收集材料
  -> 按 Story / Branch / Scene 过滤
  -> 按 Agent 身份和角色知识过滤
  -> 检索相关材料
  -> 编译结构化状态
  -> 选择历史和摘要
  -> 去重、检查覆盖范围
  -> 分配 Token 预算
  -> 渲染为 DirectorView / ActorView / ChroniclerView
  -> 泄漏检查
  -> 调用模型
```

所有实现都必须遵守以下硬约束：

1. 上下文只能来自当前执行快照可达的 Story、Branch、Scene 和资源版本。
2. Actor 只能读取自己有资格知道的内容；Director 的全知不能通过 `ActorBrief` 泄露给 Actor。
3. Turn 未提交前，临时内容只能在当前 Turn 内按可见性使用。
4. 作者指令是否对角色可见，由作者指令本身的可见性和故事内观察规则决定。
5. 结构化状态是事实校验依据，模型生成的自然语言不是事实数据库。
6. 任何材料都必须带来源、作用域和优先级，不能把无来源文本直接拼进上下文。
7. Token 不够时按完整 `ContextItem` 裁剪，不能从一段材料中间截断字符串。
8. 编排插件可以改变材料选择和顺序，但不能绕过上述约束。

## 2. 基本对象

### 2.1 ContextItem

`ContextItem` 是上下文编排器处理的最小材料单位。它不是数据库表，也不要求一项材料对应一条消息。

```ts
interface ContextItem {
  id: string;
  kind:
    | "agent_rule"
    | "character_definition"
    | "world_rule"
    | "public_state"
    | "actor_state"
    | "actor_memory"
    | "recent_narrative"
    | "scene_summary"
    | "arc_summary"
    | "turn_summary"
    | "story_summary"
    | "turn_input"
    | "author_directive"
    | "director_plan"
    | "actor_brief"
    | "working_beat"
    | "tool_result"
    | "plugin_material";
  sourceId: string;
  branchId: string;
  visibility: "director" | "actor" | "chronicler";
  priority: "required" | "high" | "normal" | "optional";
  content: unknown;
  coveredThroughTurnId?: string;
  validAt?: string;
  tokenEstimate?: number;
  provenance: {
    sourceType: string;
    sourceIds: string[];
    generatedBy?: string;
  };
}
```

`content` 可以是结构化对象，也可以是短文本。上下文编译器负责将它转换成稳定的模型输入，不把数据库中的原始 JSON 原样暴露给模型。

### 2.2 ContextSnapshot

一次模型调用使用一个不可变的上下文快照：

```ts
interface ContextSnapshot {
  id: string;
  storyId: string;
  branchId: string;
  checkpointId: string;
  turnId: string;
  attemptId: string;
  role: "director" | "actor" | "chronicler";
  actorId?: string;
  sourceVersions: Record<string, string>;
  items: ContextItem[];
  messages: Array<{
    role: "system" | "user" | "assistant" | "tool";
    content: string;
  }>;
  estimatedTokens: number;
  omittedItemIds: string[];
  leakageCheck: "passed" | "failed";
}
```

模型请求必须记录所使用的 `ContextSnapshot` 或等价的版本引用。重试请求使用同一输入快照时，才能明确它是在重试，而不是偷偷换了一套上下文。

MVP 默认保存完整快照，不加密，不自动过期；所有快照共用 300 MB 默认配额。用户可以手动清理，达到配额时不自动删除旧快照，而是提示清理空间。

### 2.3 材料的三个属性

编排时必须分别处理以下三个属性，不能合并成一个 `scope` 字段：

| 属性 | 作用 | 例子 |
| --- | --- | --- |
| 来源 | 说明材料从哪里来 | 事件、角色记忆、Worldbook |
| 可见性 | 说明哪个 Agent 可以读取 | `actor`、`director` |
| 优先级 | 说明预算不足时是否保留 | `required`、`optional` |

例如 Bob 的个人记忆可以是 `source=actor_memory`、`visibility=actor`、`priority=high`；它不能因为优先级很高就被交给 Alice。

## 3. 编排流水线

### 3.1 收集

编排器从以下来源收集候选材料：

- Agent 身份和输出协议。
- 当前 Story、Branch、Scene 和执行配置。
- 当前角色卡、用户人设和适用 Worldbook 条目。
- 当前公共状态和角色专属状态。
- 角色有资格读取的个人记忆。
- 已覆盖范围明确的 TurnSummary、SceneSummary、ArcSummary 和 StorySummary。
- 摘要尚未覆盖的最近正式 Turn。
- 当前 Turn 的用户输入、作者指令和已接受 Beat。
- 已授权的工具结果、媒体结果和插件材料。

收集阶段只按来源和当前检查点取候选，不根据模型自由猜测“可能有用”的秘密。

### 3.2 过滤

过滤顺序固定为：

1. Story 和 Branch 可达性。
2. Checkpoint 的时间边界。
3. Scene 和资源版本适用范围。
4. Agent 身份。
5. Actor 的观察条件和个人知识范围。
6. 材料有效状态和失效时间。

先做权限过滤，再做相关性排序。不能先把所有秘密放进候选集，再靠排序器“尽量不选”。

### 3.3 检索

MVP 使用 SQLite 条件查询和全文检索。默认相关性顺序为：

1. 当前 Turn 必须使用的输入和临时状态。
2. 当前 Scene 的必需状态。
3. 角色身份和当前行动直接相关的记忆。
4. 最近且未被摘要覆盖的正式叙事。
5. 与当前目标、实体和地点相关的摘要。
6. 其他适用的 Worldbook 条目。

未来可以加入关键词、全文、图结构或向量检索。检索方式可以替换，权限过滤、Branch 过滤和来源追踪不能替换。

### 3.4 编译

结构化材料在这里转换为简洁、稳定的文本或工具调用参数。例如：

```text
当前时间：午夜
当前地点：酒馆后门
在场角色：Alice、Bob
公开可见物品：油灯、木桌、书架
```

编译器不应输出数据库字段名堆叠，也不应把同一事实同时以十种自然语言重复描述。

### 3.5 去重和覆盖检查

每个摘要记录都有 `coveredThroughTurnId`。如果摘要已经覆盖到 Turn 20，则最近原文只能从 Turn 21 开始选择。

同一事实同时出现在结构化状态、摘要和近期原文中时，默认保留：

1. 当前结构化状态。
2. 尚未被摘要覆盖的最近原文。
3. 摘要中的背景描述。

重复材料被合并或删除，并在编排日志中记录被省略的来源。摘要与状态冲突时，不静默拼接两个版本：以有效事件投影为准，并标记冲突供 Director 或 Chronicler 处理。

## 4. DirectorView

Director 需要知道足够多的信息来规划剧情，但不需要每次读取整部小说的原文。

默认内容：

```text
Agent 运行规则
+ 当前 Branch 的结构化事实和状态
+ 当前 Scene 状态
+ 参与角色、控制状态和剧情权限
+ 用户角色输入
+ 作者指令
+ 相关角色的目标、关系和记忆摘要
+ 未被摘要覆盖的近期叙事
+ 相关 Worldbook 条目
+ Archivist / 工具返回的带来源资料
```

Director 可以读取当前 Branch 的完整事实视图，包括未公开事件，但必须知道材料的公开性。看到秘密不等于可以把秘密写进所有角色的 `ActorBrief`。

Director 默认不读取：

- 其他 Branch 的后续内容。
- 没有适用条件的整本 Worldbook 原文。
- 已被高层摘要替代且与当前决策无关的全部旧 Turn。
- 任何没有来源的插件内部缓存。

Director 输出的是计划，不是事实。计划、未执行的目标和被废弃的候选不得进入正式事件或角色记忆。

## 5. ActorView

ActorView 必须按一个具体 `actorId` 构建。不同 Actor 即使参加同一个 Beat，也必须分别编译上下文。

默认内容：

```text
Agent 运行规则
+ 角色卡和说话风格
+ 适用的 WorldRule / Worldbook 条目
+ 当前公共场景状态
+ 角色自己的结构化状态
+ 角色自己的 ActorMemory
+ 当前 Turn 中已接受且对该角色可见的 Beat
+ 当前 StorySummary
+ 最近已提交 Turn 的 TurnSummary
+ 局部 ActorBrief
+ 当前用户输入或作者指令中明确授权可见的部分
+ 输出格式要求
```

Actor 不得读取：

- 其他角色的个人记忆、私有状态和隐藏目标。
- Director 的完整计划、重规划触发器和内部分析。
- Chronicler 的事件提案、摘要草稿和冲突判断。
- 未被该角色观察到的秘密事件。
- 对其他角色隐藏的作者指令。
- 其他 Branch 的内容。

### 5.1 ActorBrief 的转换规则

Director 的计划必须先转换成角色能理解、但不泄露越权事实的 `ActorBrief`：

```ts
interface ActorBrief {
  actorId: string;
  objective: string;
  actionGuidance?: string;
  emotionalGuidance?: string;
  knownPremises: string[];
  forbiddenAssumptions: string[];
  completionHint?: string;
  sourcePlanId: string;
}
```

例子：

```text
Director 知道：Alice 把钥匙藏起来，Bob 没有看见。

给 Bob 的 ActorBrief：
询问 Alice 是否见过钥匙，表现出怀疑和焦虑。
```

不能写成：

```text
因为 Alice 把钥匙藏在书架后面，所以询问她。
```

`knownPremises` 只能写 Bob 已经知道或本 Beat 中可以观察到的前提。ActorBrief 生成后必须再次经过角色知识检查。

### 5.2 当前 Turn 的临时内容

Actor 可以读取当前 Turn 中前面已接受的 Beat，但必须同时满足：

1. Beat 属于同一个 Turn 和 Attempt。
2. Beat 已经被 Runtime 接受，不是流式草稿或被废弃候选。
3. 该内容按 `observerIds` 和场景观察规则对当前角色可见。
4. 内容没有被用户撤销或被后续临时修正覆盖。

当前 Turn 的临时内容只用于继续本轮演出。Turn 未提交前，它不能出现在下一个 Turn 的 ActorView、长期记忆或分支检查点中。

## 6. ChroniclerView

Chronicler 的任务是记录已经发生的内容，不是继续写剧情。

默认内容：

```text
Agent 运行规则
+ Turn 开始前的正式状态和 Branch head
+ 本 Turn 已接受的完整 Beat
+ 用户角色输入
+ 作者指令及其解析结果
+ Actor 提出的状态变更
+ 角色实际可见性和观察结果
+ 必要的历史摘要
+ 适用的 WorldRule
```

Chronicler 不读取或不采纳：

- 尚未执行的 Director 计划。
- 被丢弃的 Actor 候选。
- 流式残句和未接受草稿。
- 没有实际结果的工具调用意图。
- 需要靠自己继续创作才能成立的新剧情。

Chronicler 输出的事件、公开状态和角色记忆提案必须带来源事件和基准状态版本。无法从 Turn 内容证明的结论必须标记为待确认，不能直接提交。

### 6.1 Chronicler 的调用时机

- Turn 正常结束时：必须完成一次正式整理，或使用已经通过校验的确定性结果。
- 用户采纳完整前缀时：必须重新整理该前缀，再作为完整 Turn 提交。
- Scene / Arc 结束时：在 Turn 提交流程中同步更新对应摘要；不另开一个绕过提交边界的异步 Chronicler 流程。

因此，Chronicler 不在 Beat 结束时调用；每个正式提交的 Turn 只在结束时调用一次，并且必须完成摘要、事件、状态和记忆整理。

## 7. TurnWorkingState 的上下文规则

`TurnWorkingState` 是当前 Turn 的临时上下文，不是第二套数据库事实。

```ts
interface TurnWorkingState {
  turnId: string;
  attemptId: string;
  baseCheckpointId: string;
  acceptedBeatIds: string[];
  temporarySegments: string[];
  temporaryMutations: string[];
  visibleThroughBeatId: Record<string, string>;
  status: "running" | "interrupted" | "ready_for_chronicler" | "discarded";
}
```

规则如下：

1. 所有 Beat 都以 Turn 开始时的正式状态为基准，加上此前已接受且可见的临时内容。
2. 后续 Beat 不得读取另一个 Turn 的临时状态。
3. 同一 Turn 内的临时状态不能更新正式 `Branch head`。
4. 用户取消后，未完成的草稿不能进入 `TurnWorkingState` 的已接受前缀。
5. Turn 回退时，整个 `TurnWorkingState` 作废；采纳前缀时，只保留明确完整的前缀并重新整理。
6. Chronicler 失败时保留临时状态，但禁止开始下一个 Turn。

## 8. 结构化状态和自然语言材料

### 8.1 优先结构化

以下内容优先结构化保存，再由编译器转换为模型可读形式：

- 当前时间、地点和在场角色。
- 角色位置、物品和控制状态；伤势不在 MVP 中作为结构化字段。
- 物品位置、归属和公开状态。
- 角色关系及其有效范围。
- 世界规则的来源、优先级、适用条件和版本。
- 角色记忆的角色 ID、类型、来源、置信度和状态。
- Turn、Beat、Checkpoint 和摘要覆盖游标。
- 工具结果、媒体结果和插件状态的来源引用。

结构化的目的，是让 Runtime 能校验、过滤、分支和恢复；不是要求模型直接阅读一堆字段名。

### 8.2 保留自然语言

以下内容通常保留自然语言：

- 角色性格、语气和表现风格。
- 场景气氛和文学语境。
- 角色记忆的短文本表达。
- TurnSummary、SceneSummary、ArcSummary 和 StorySummary。
- 作者指令。
- 无法稳定拆分的原始角色卡或 Worldbook 条目。

自然语言材料也必须有来源、作用域、有效范围和预算。不能因为它是文本就永久累积。

## 9. 历史、摘要和长上下文

### 9.1 最近记录的范围

“最近记录”不按固定的 Turn 数量定义，而按以下条件选择：

1. 从摘要覆盖游标之后的第一个正式 Turn 开始。
2. 优先选择对当前角色、地点、目标和参与者有直接关系的 Turn。
3. 在预算允许时向更早的 Turn 扩展。
4. 遇到已被摘要覆盖的范围立即停止，不重复注入。

因此，短对话可能保留很多最近 Turn，长而复杂的 Turn 可能只保留少量；实际范围由内容大小和 Agent 预算决定。

### 9.2 摘要层级

默认使用四层摘要：

```text
TurnSummary
  -> SceneSummary
  -> ArcSummary
  -> StorySummary
```

Turn 结束时同步生成 `TurnSummary`，并更新当前有效的 `StorySummary`。Actor 的历史剧情材料默认只使用当前 Turn 的已接受 Beat、StorySummary 和最近已提交 Turn 的 TurnSummary，不再直接拼接一长段历史原文。

不同 Agent 的默认选择：

| Agent | 默认历史材料 |
| --- | --- |
| Director | 当前 SceneSummary、相关 ArcSummary、必要的 StorySummary、相关最近 Turn |
| Actor | 当前 Turn 已接受 Beat、StorySummary、最近 TurnSummary、角色相关记忆 |
| Chronicler | 本 Turn 完整内容、Turn 开始前的摘要和必要结构化状态 |

摘要不是事实的唯一来源。关键状态、秘密公开情况、物品位置、角色关系和未完成目标必须保留结构化记录。

### 9.3 摘要也超出预算时

当 StorySummary 本身过长，系统按完整摘要段落和主题重新生成更高层的新版本：

```text
旧 StorySummary + 新 ArcSummary
  -> 新 StorySummary
```

新版本通过来源、覆盖范围和基本事实检查后，才替换当前版本；旧版本保留以便审计和重建。

预算不足时的裁剪顺序是：

1. 删除重复的自然语言材料。
2. 删除不相关的 Worldbook 条目和旧摘要。
3. 缩短可压缩摘要，保留事实锚点。
4. 减少普通优先级的近期叙事。
5. 如果连 `required` 材料也放不下，则停止本次模型调用并返回上下文预算错误。

不能直接从摘要开头截断，也不能删除结构化事实来换取模型调用成功。

## 10. Token 预算

预算由模型连接配置、Agent 角色和当前任务共同决定。编排器必须先预留模型输出空间，再分配输入材料。

MVP 使用以下计算方式：

```text
输入预算 = 模型上下文上限 - 输出预留 - 安全余量
```

MVP 的默认预算规则如下。实际模型连接可以覆盖这些值，但必须保存覆盖结果到 `ExecutionProfile`，不能在运行中悄悄改变。

```text
safetyMargin = max(512, ceil(contextWindow * 0.08))
outputReserve = roleDefaultReserve[role]
inputBudget = contextWindow - safetyMargin - outputReserve
```

默认输出预留：

| Agent | 默认输出预留 | 用途 |
| --- | ---: | --- |
| Director | 1,500 tokens | 计划、参与者、结束条件和必要的 SceneMutation |
| Actor | 1,000 tokens | 一条 Beat 的台词、动作和结构化提案 |
| Chronicler | 2,000 tokens | 事件、状态、记忆、TurnSummary 和 StorySummary |
| Archivist | 1,200 tokens | 带来源的检索整理结果 |

如果模型上下文窗口小于 8,000 tokens，Runtime 将安全余量固定为 512，并把 Actor 预留下调到 800、Director 下调到 1,200、Chronicler 下调到 1,600；仍无法容纳 `required` 材料时直接返回 `context_budget_exceeded`。输出预留不是模型强制上限，但超出预留后必须记录预算超用，并停止继续追加材料。

MVP 不用“把摘要按字符直接截断”的方式解决超长问题。StorySummary 超预算时，先按覆盖范围生成更高层摘要；仍超预算时按完整摘要段落和主题裁剪；任何必需的当前状态、权限规则、作者指令和当前输入都不能被删掉。实际 Provider 返回上下文限制错误时停止调用、记录原因，不自动无限重试。

默认优先级：

1. `required`：Agent 身份、输出协议、当前输入、作者指令、当前状态、必要临时内容。
2. `high`：当前 Scene、相关角色记忆、最近正式 Turn、适用 Worldbook。
3. `normal`：相关摘要、关系背景和较旧剧情。
4. `optional`：不相关世界书、重复说明、低置信度旧记忆和装饰性文本。

每个 Agent 应有独立预算，不允许 Director 的大预算自动挤占 Actor 的输出空间。编排日志至少记录总预算、已用估算、保留项和省略项。

## 11. Worldbook 和 Preset 兼容

### 11.1 Worldbook

一个 Story 可以同时绑定多本 Worldbook。编排器对每本 Worldbook 独立执行：

1. 版本选择。
2. Story、Branch、Scene 和 Actor 作用域过滤。
3. 条件激活。
4. 优先级排序。
5. Token 预算裁剪。

Worldbook 条目进入上下文时保留来源和书本 ID。不能在导入时永久合并所有书本，否则无法解释冲突、停用某本书或在分支中使用不同版本。

### 11.2 Preset

酒馆 Preset 在本系统中作为 `ContextPolicy` 兼容：

```ts
interface ContextPolicy {
  id: string;
  version: string;
  systemInstructions?: string[];
  messageLayout?: string;
  worldbookPlacement?: string;
  characterPlacement?: string;
  historyFormat?: string;
  authorNote?: string;
  outputFormat?: string;
  modelParameters?: Record<string, unknown>;
}
```

Preset 可以影响提示词、材料顺序、历史格式和模型参数，但不能改变：

- Actor 的知识权限。
- Branch 隔离。
- Turn 提交边界。
- 事件和记忆的来源校验。
- 用户控制角色的授权边界。

原始 Preset 中无法映射的字段必须保留并报告兼容状态，不能无提示丢弃。

## 12. 辅助 Agent 和工具

Director 不应承担所有检索、整理和外部操作。系统允许加入只读的辅助 Agent，例如：

- `Archivist`：从已通过权限过滤的历史材料中寻找相关资料。
- `Summarizer`：生成 TurnSummary、SceneSummary、ArcSummary 和 StorySummary。
- `Researcher`：调用已授权的网络或文件工具，返回带来源的结果。
- `MediaAgent`：生成图片、音频等 Artifact，不直接改变叙事事实。

辅助 Agent 的默认边界：

1. 只能接收调用方已经有资格读取的材料，不能借“帮忙检索”扩大权限。
2. 返回结果必须带来源、时间和工具调用记录。
3. 默认只读，不能直接提交事件、状态或记忆。
4. 需要修改故事时，必须返回版本化 mutation，由主 Runtime 统一校验和提交。
5. 失败、超时或来源不明时，结果不能当作事实写入上下文。

MVP 使用本地 LanceDB 向量索引和 Archivist 检索 Agent。LanceDB 数据目录为 `$APP_DATA_DIR/vector`；SQLite 保存来源、Branch、角色权限、内容哈希、嵌入模型和索引引用，SQLite 仍是事实来源。向量索引损坏或版本不匹配时，Runtime 可以从 SQLite 重新构建。

向量索引不是事实来源，也不能替代结构化状态、摘要覆盖游标或角色知识过滤。检索顺序必须是：先在 SQLite 中按 Story、Branch、来源有效性、角色权限和时间范围过滤候选，再把合格候选交给 LanceDB 做向量/全文检索，最后由 Archivist 整理带来源结果。不能把全部向量库交给排序器后再补权限过滤。

## 13. 插件修改边界

插件可以扩展或替换以下部分：

- 材料收集器。
- 检索器和排序器。
- ContextItem 编译器。
- 节点顺序和预算策略。
- Director、Actor、Chronicler 的视图转换。
- 摘要和 Archivist 策略。
- 媒体和外部工具材料。

插件必须通过宿主提供的受限接口工作，至少声明：

- 可读取的材料类型和角色范围。
- 可写入的命名空间。
- 所需模型、工具和预算。
- 输入输出 schema 版本。
- 是否允许访问作者指令和隐藏材料。

插件的自定义状态可以使用 JSON。宿主不强制规定所有插件必须采用同一业务结构，但建议插件遵守以下约定：

```json
{
  "schemaVersion": "1",
  "status": "active",
  "data": {},
  "derived": {},
  "sourceRefs": [],
  "updatedAt": "2026-09-22T00:00:00Z"
}
```

其中 `data` 保存插件拥有的状态，`derived` 保存可重建结果，`sourceRefs` 保存来源事件或 Turn。插件仍必须声明 schema 版本、Branch 作用域和迁移方式；这套结构是建议，不是核心 Runtime 强制的业务字段。

插件 Manifest 和能力注册机制参考 DSH 风格：插件声明身份、版本、宿主 API 版本、能力、依赖、权限、配置 schema、状态 schema 和迁移入口；安装、启用、停用、升级和卸载都由宿主记录。插件不得因为 Manifest 声明更高优先级就静默替换用户当前选择的实现。

插件不能：

- 直接查询未过滤的全库事件或记忆。
- 修改 `visibility` 来扩大 Actor 权限。
- 绕过 Branch、Checkpoint、Turn 提交闸门或状态版本校验。
- 把导演计划、其他角色记忆或隐藏作者指令直接交给 Actor。
- 用全局缓存跨 Story 或 Branch 复用上下文。

后端 Node 插件属于自托管环境中的可信服务器代码。上下文接口可以减少误用和插件之间的耦合，但首版不宣称能够隔离恶意插件代码。

## 14. 已确定的实现边界

1. Preset、Worldbook、正则后处理和 UI 扩展的兼容范围以《酒馆兼容矩阵》为准。
2. LanceDB 是 MVP 默认向量索引实现；SQLite 是事实和权限元数据来源。
3. 核心结构化状态以《核心状态JSON Schema》为准；插件状态不强制采用核心状态结构。
4. 插件可以注册新的 `ContextItem.kind`，但必须携带版本化 schema 和来源，且不能绕过权限、Branch 和 Turn 提交边界。

## 15. 验收场景

| ID | 场景 | 必须满足的结果 |
| --- | --- | --- |
| C01 | Alice 知道秘密，Bob 不知道 | Alice 的 ActorView 可见；Bob 的 ActorView、ActorBrief 和工具结果均不可见 |
| C02 | 多本 Worldbook 共存 | 条目按书本、版本、作用域和激活条件独立选择，不永久合并 |
| C03 | Director 规划 Bob 询问 Alice | Bob 只收到“询问并表现怀疑”等目标，不收到 Alice 藏钥匙的秘密原因 |
| C04 | Bob 读取 Alice 前一个 Beat | 仅当 Beat 已接受且按观察规则可见时进入 Bob 的当前 Turn 上下文 |
| C05 | Turn 未提交时断流 | 临时 Beat 不进入下一 Turn、长期记忆或分支检查点 |
| C06 | 摘要已覆盖 Turn 1-20 | Director 不同时注入覆盖同一范围的摘要和 Turn 原文 |
| C07 | StorySummary 超预算 | 生成有覆盖范围的新摘要版本，不能直接截断旧摘要开头 |
| C08 | required 材料超预算 | 停止模型调用并返回预算错误，不删除角色权限规则或当前输入 |
| C09 | 只读 Archivist 搜索秘密 | 搜索结果不超过调用方权限，且每条结果带来源 |
| C10 | Preset 要求把秘密放入 Actor 提示词 | 兼容层拒绝越权操作，Preset 不能绕过知识过滤 |
| C11 | 插件提供自定义排序器 | 可以调整合格材料顺序，但不能读取过滤前的其他角色记忆 |
| C12 | 重试同一模型请求 | 使用记录中的同一 `ContextSnapshot`，或明确记录新的上下文版本 |
