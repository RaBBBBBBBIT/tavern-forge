## 1. 文档约定

本文正文描述当前版本采用的领域规则和运行边界。实现默认会在“当前 MVP 默认”或配套规格中单独标明；未列入正文的行为不应由实现自行推断。类型片段用于表达语义，不构成完整 SDK 或数据库定义。

## 2. 产品边界

系统以现代 Agent loop 支持叙事互动，不以复刻酒馆界面为目标，也不将“支持插件”本身视为差异化。

### 2.1 核心要求

1. 兼容酒馆角色卡、世界书及预设，同时保留原生编排方案的发展空间。
2. 模型连接允许用户手动配置；MVP 的首个接入目标为 DeepSeek API。
3. 支持沉浸聊天与小说两种交互模式，能在同一故事中切换并共享状态。
4. 一次用户输入可以触发多条输出、多名角色参与和同一角色连续发言；一个 Beat 默认生成一条消息，一个 Turn 最多生成 10 个 Beat。
5. Director 统一规划参与者、顺序、目标、动作、情绪及结束条件；Actor 执行角色表现；Chronicler 汇总已发生内容并提出状态更新。
6. Director 不逐句审批，只在需要重新规划时介入。发言顺序可以是 `Bob -> Bob -> Alice -> Bob`。达到 10 个 Beat 后必须停止当前 Turn，后续推进由用户点击“继续”创建新的 Turn。
7. 三类 Agent 及工作流开放接口供插件增强或替换，社区还可扩展记忆、上下文、媒体、UI 和状态系统。
8. 用户可查看和修改本地故事内全部叙事状态；Actor 只能获得其应当知道的内容。
9. 剧情推进权限与输出展示形式独立配置。
10. 失败、取消和断流应停止当前执行并保留已有内容，支持请求级和用户输入级重试。
11. 记忆系统由本项目自行管理，不把 DeepSeek Harness、pi 或其他外部 Agent 的记忆模型作为兼容目标；插件 Manifest 和能力注册机制可以参考 DSH 风格。
12. 用户可维护多套人设；一套人设在故事内作为可选择的用户控制角色，拥有独立的身份、关系与知识状态。
13. 项目以开源自托管 Web 应用交付：后端使用 Node.js，数据库使用 SQLite；前端和接口细节由配套规格定义。
14. 前后端代码与构建独立；生产环境通过一个 Node 应用实例执行 Runtime、持有数据库与模型凭据。
15. 自托管用户可安装在后端执行的 Node 插件；此类插件默认属于受信任服务器代码，而非安全沙箱中的第三方脚本。
16. 一个 Turn 最多携带一个作者指令文本块；需要表达多个要求时，用户在同一文本块中分行输入。

### 2.2 当前 MVP 默认

- 采用多场景、多分支；每个分支在 MVP 中只有一个活动场景和一个活动 Turn 执行者。
- 所有叙事变化可追溯；重试和编辑不能静默污染已确认历史。
- 用已提交叙事事件作为事实来源，状态投影和记忆是可追溯的派生数据。
- 提供一个基础状态查看/修改入口；复杂作者控制台交给社区。
- 部分流式输出保留为草稿；只有 Turn 正式提交后才进入正式叙事、状态和角色记忆。

## 3. 用户使用模型

### 3.1 四个相互独立的维度

| 维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 交互模式 | 用户这次输入代表什么？ | 角色内发言、作者写作指令 |
| 剧情权限 | 系统可以替用户做多少决定？ | 严格控制、补全小动作、自动推进、旁观 |
| 展示配置 | 已生成内容怎样呈现？ | 气泡、纯对话、动作、小说段落 |
| 工作流配置 | 使用哪些 Agent、策略和插件？ | 默认场景循环、社区导演、社区记忆 |

聊天/小说模式可以提供默认组合，但不能把以上四项硬绑定。例如，小说模式同样可以禁止代写用户角色的决定；聊天模式也可以允许完全旁观。

### 3.2 模式切换

- 沉浸聊天默认将输入理解为用户角色的台词或行动；显式作者指令使用独立输入通道或明确标记。
- 小说模式默认将输入理解为写作意图，不将“下一段写两人争吵”存成故事内台词。
- 切换模式不创建新世界、不清空记忆、不改变历史事实，也不隐式切换用户人设或改变角色身份。
- 模式、预设、插件版本与参数在 Turn 开始时固定为执行快照。执行中切换默认从下一个 Turn 生效；立即生效需要先停止当前执行。
- 切换为小说展示不等于自动重写历史。对历史进行文学改写是另一个可追踪的生成任务。

### 3.3 剧情推进权限

| 用户选项 | 建议语义 |
| --- | --- |
| 严格控制 | NPC 可正常回应，但不得代写任一用户控制角色的台词、内心、动作和选择；涉及其决定时交回用户 |
| 允许补全小动作 | 允许补足无重大后果的衔接动作，不代替用户控制角色的承诺、立场、重大行动或内心决定 |
| 允许自动推进剧情 | 允许场景推进、时间流逝及已授权用户控制角色的日常行为；重大决定仍受单独授权边界限制 |
| 完全旁观 | 允许系统安排包括用户控制角色在内的演出；用户仍可随时停止或修改 |

这四档是权限配置的预设，而不是四套硬编码 prompt。底层至少表达 `userSpeech`、`userActions`、`userInnerState`、`majorDecisions`、`timeAdvance` 等权限；具体分级阈值待验证。

核心负责保存和执行用户选定的权限，社区可提供更细的规则与控制面板。权限不能仅由导演在自然语言中“记住”。

### 3.4 输出表现模型

“纯对话”和“显示动作”属于内容可见性；“聊天气泡”和“小说段落”属于布局。运行时必须将二者分离：同一叙事事件可投影为不同表现形式，表现切换不得改写事实。

隐藏动作或情绪仅影响显示，不撤销已发生动作。角色内心即使对用户可见，也不会因此变成其他角色可知的内容。具体页面布局、移动端编辑与状态展示见《前端交互规格》。

### 3.5 复合回合输入

一个 Turn 可以同时包含：

- 一个或多个用户控制角色的故事内输入，具体归属由 `InputAttribution` 标明。
- 零个或一个作者指令文本块。

作者指令不是第二条角色消息，也不是直接暴露给模型的 `system` message。它由 Runtime 保存为操控者输入，参与当前 Turn 的约束、剧情重规划或状态修正。

```ts
interface TurnInput {
  actorInputs: Array<{
    actorId: string;
    content: string;
  }>;
  authorDirective?: AuthorDirectiveInput;
}

interface AuthorDirectiveInput {
  content: string;
  timing: "before" | "after";
  scope: "turn" | "scene" | "branch";
  visibility: "hidden" | "narrator" | "actors";
  visibleToActorIds?: string[];
}
```

`authorDirective` 缺省表示本 Turn 没有作者指令；不允许使用数组表达多个并列作者指令。文本内部可以使用多行或项目符号表达多个要求，解析后的约束仍属于同一个作者输入事件和同一个幂等提交单元。

`before` 表示作者约束先于本 Turn 的故事内输入生效；`after` 表示先提交本 Turn 的用户故事内输入，再应用作者约束，然后 Director 规划后续角色输出。v0.1 不支持“插在第 N 个生成 Beat 之间”的 `inline` 指令，用户需要在该 Beat 结束后另起 Turn。全故事范围的基础设定修改不使用作者指令，必须走明确的 Story 状态编辑或资产版本更新，避免绕开 Branch 隔离。

`visibility: hidden` 只允许 Director、Chronicler 和获授权插件读取原始指令；`narrator` 表示指令通过旁白或事件被故事化，角色是否知道仍由观察规则决定；`actors` 表示将指令内容直接提供给 `visibleToActorIds` 中的角色。使用 `actors` 时该数组必须非空，且不得默认广播给全部角色。

若同一作者指令包含互相冲突的要求，Runtime 将其视为一个作者输入交给解析/校验流程；无法确定时暂停并要求用户修改或确认，不能拆成多条后按任意顺序执行。

作者指令原文首先是操控者输入，不自动等于已经发生的事实。Runtime 将其解析为以下一种或多种效果提案：

- **持续约束**：例如“Bob 本场景不能离开”，在对应 `scope` 内约束 Director。
- **强制下一步**：例如“让 Alice 下一步质问 Bob”，必须进入下一份 Plan；无法执行时暂停并说明原因，不能静默忽略。
- **一次性叙事事件**：例如“门外现在响起三声敲门”，按 `timing` 提交一次叙事事件，不因 `scope` 在后续 Turn 重复发生。
- **明确状态修正**：例如“Alice 现在知道 Bob 在说谎”，产生带作者指令来源的知识 mutation，不把该知识自动广播给其他角色。

`scope` 只控制持续约束的最长有效期；一次性事件和状态修正只提交一次。措辞为“之后发现”“下一步发生”时按未来约束处理；措辞为“现在已经”“设为”时可按立即事件/修正处理。无法确定是未来约束还是立即修正时必须要求用户确认。

作者指令可以明确操控 `controller: user` 的角色，因为行为来自用户本人；提交事件的来源仍标记为作者指令，不能伪装成 Actor 自主决定。Director 不得把这一例外扩展为后续自动控制权。

## 4. 领域模型

```text
WorldDefinition（版本化角色卡、世界书、基础设定）
  └─ Story（一次独立故事/游玩实例，亦可称 Campaign）
      ├─ Branch A
      │   ├─ Scene 1
      │   └─ Scene 2（活动场景）
      └─ Branch B（从 A 的某个检查点分出）
          └─ Scene 1 的另一种后续
```

场景是时间线中的叙事单位，不是分支的替代物。另一条时间线属于另一个 Branch，不应被建模成同一分支中的普通 Scene。

| 对象 | 职责与边界 |
| --- | --- |
| WorldDefinition | 可复用基础资源，不存某条时间线独有的剧情结果 |
| AssetRevision | 一份角色卡、世界书、预设或角色定义的不可变版本，保留源格式与扩展字段 |
| Story | 组织一次故事的分支、配置和资源绑定 |
| Branch | 时间线身份、父检查点、当前 head、活动场景和角色状态 |
| Scene | 地点、叙事时间、在场者和场景生命周期；由 Director 提议管理，Runtime 校验并提交，地点切换不强制等于换场景 |
| CharacterDefinition | 角色身份及设定，可源自卡片、世界书或用户创建 |
| ActorInstance | 某故事中的角色实例；运行状态按分支/检查点读取，不是必须常驻的进程 |
| UserOperator | 故事外的用户账户/操作者，可查看、编辑和配置故事，不等于任何一个故事内人物 |
| UserPersonaDefinition | 可复用的用户人设档案，含名称、描述、头像、默认口吻及来源版本 |
| UserActorInstance | UserPersonaDefinition 绑定到 Story 后形成的用户控制角色；拥有独立角色 ID、关系、知识和分支状态 |
| ActorControlAssignment | 指定 Branch 中某个角色当前由用户还是 Agent 控制；属于运行配置，不是故事内事实 |
| InputAttribution | 一条用户输入的来源：故事外作者/OOC，或某个当前由用户控制的 ActorInstance |
| Turn | 一次用户输入或显式继续命令代表的逻辑互动 |
| TurnAttempt | Turn 的一次执行尝试，可包含多个计划、Beat、模型请求与工具调用 |
| ScenePlan | 导演的有限演出计划，不是已经发生的事实 |
| Beat | Turn 内的临时执行与展示单元，可产生同一角色的多条消息；默认不能单独成为分支正式事实 |
| ModelRequestAttempt | 一次具体模型请求及其输入版本、输出流和结束原因 |
| NarrativeEvent | 已确认发生的台词、动作、观察、修正等叙事事件 |
| StateProjection | 从有效事件和修正得到的当前状态视图，带版本和处理水位 |
| MemoryRecord | 只属于一个角色的记忆记录；字段和生命周期见《记忆与上下文材料规格》 |
| Artifact | 消息、章节、图片等呈现对象，关联生成来源与叙事事件 |
| Checkpoint | 分支历史位置及其状态/配置引用；用于分叉、恢复和重试 |

### 4.1 用户多套人设

用户操作者和用户人设必须分离。前者拥有故事数据的最终控制权；后者是故事中的 Actor，和 NPC 一样有角色身份和可知范围。

```ts
interface UserPersonaDefinition {
  id: string;
  revisionId: string;
  name: string;
  profile: unknown;
  defaultPresentation?: unknown;
}

interface UserActorInstance {
  id: string;
  storyId: string;
  personaRevisionId: string;
  controllerId: string;
  role: "user_controlled";
}

interface ActorControlAssignment {
  branchId: string;
  actorId: string;
  controller: "user" | "agent";
  controlVersion: number;
}

interface InputAttribution {
  kind: "author" | "out_of_character" | "character";
  senderActorId?: string;
}
```

- 一个用户可保存多份 `UserPersonaDefinition`，同一 Story 可绑定多个 `UserActorInstance`；一份档案可在不同 Story 中复用，但实例状态不复用。
- 每条故事内输入必须归属到一个明确的 `senderActorId`。作者指令、状态编辑和 OOC 输入归属用户操作者，不伪装成任何人设的发言。
- UI 可以提供“当前人设”作为输入默认值，但发送记录必须保存实际归属，不能依赖之后会变化的全局当前值。
- 同一 Scene 可存在多个用户控制角色。用户可以轮流扮演；只有在相应剧情权限允许时，系统才可替其中指定角色生成表现。
- 每个 Branch 为每个 Actor 保存一份 `ActorControlAssignment`。用户人设默认由 `user` 控制，NPC 默认由 `agent` 控制；临时接管 NPC 是将该 Branch 中的 assignment 改为 `user`，交还是改回 `agent`。
- `controller: user` 时，Director 不得为该角色安排自动 Actor Beat。用户可通过该角色的 `ActorInput` 或作者指令控制其行为。`controller: agent` 时，Director 才能在剧情权限允许的范围内安排该角色。
- 控制状态不是角色可知事实，不进入角色记忆。它必须写入执行审计并带版本；生成过程中修改控制状态会使依赖旧版本的 Plan 失效。
- 创建子 Branch 时继承分叉点的控制状态，之后各 Branch 独立修改。切换页面上的当前输入角色不等于修改控制状态；选择一个尚未接管的 NPC 时必须先提交接管操作。
- 每个用户角色的关系、物品、当前位置、经历和可知事实按 Branch 独立保存。用户本人可以查看全局状态，但 Runtime 自动代写、Director Brief 和其他 Actor 输入必须使用相应用户角色的知识视图。
- 人设档案的修改产生新 revision。更新某个 `UserActorInstance` 时，用户应选择仅未来使用、应用到当前分支，或从指定检查点创建替代分支；不得静默改写历史消息的归属或已发生事实。
- 切换输入人设本身没有故事内效果。若新角色尚未在场，用户必须选择将其作为新角色登场、已有在场角色接管，或在新分支中重写历史；系统不自动让角色“变身”或瞬移。

多套用户人设不是多个聊天预设。它们直接进入角色实体、知识隔离、关系系统、Director 参与者选择和消息归属。

### 4.2 状态不是单一作用域枚举

以下维度应分开保存，而不是用 `world | branch | actor | plugin` 一个字段互相排斥：

- 历史归属：哪个 Story、Branch、检查点或事件。
- 实体归属：哪个角色、场景、关系、物品。
- 知识条件：哪些角色知道、如何知道、相信程度及有效时间。
- 所有者：核心或某插件的命名空间。
- 记录性质：设定、客观事件、观察、信念、计划、派生摘要。

例如“Bob 在支线 B 中误以为 Alice 已离开”同时属于分支 B、角色 Bob 和一种信念，不能仅标记为 `actor` 后跨分支复用。

### 4.3 事件、公开状态与角色记忆

运行时必须区分以下三种对象：

```text
NarrativeEvent  真实发生或被用户明确修正的事情
PublicState     事件造成的、当前可观察或公开成立的状态投影
ActorMemory    某一个角色记得、相信、怀疑或经历过的内容
```

- `NarrativeEvent` 是事实来源，但不直接进入 Actor 上下文。事件可以被多个角色观察到，也可以完全没有角色观察到。
- `PublicState` 不是共享记忆。它只保存当前场景中角色正常观察即可知道的少量状态，例如时间、地点、在场者和公开可见物品。
- `ActorMemory` 必须绑定一个 `subjectActorId`，只属于该角色。一个事件可以不产生记忆，也可以产生一条公开可观察结果和多条不同的角色记忆。
- 角色的记忆可以是错误的。`belief`、`suspicion` 和 `experience` 不能覆盖客观事件；它们只表达该角色的认知。
- 用户、Director 和 Chronicler 可以在权限范围内读取事件或投影，但这不意味着 Actor 可以读取原始事件日志。

世界常识与故事设定统一归入 `WorldRule`。世界规则的来源可以是模型默认常识、绑定的多本 Worldbook、Story 覆盖设定或 Branch 修正；规则是否成立与某个角色是否知道该规则必须分别记录。

一个 Story 可以绑定多本 Worldbook。每本 Worldbook 保留独立版本、优先级、启用状态、条目和激活条件。运行时按当前 Story、Scene、Actor 和上下文预算选择条目，不把所有世界书永久拼成一段文本。

### 4.4 上下文材料边界

上下文编排必须区分结构化状态、角色记忆、世界规则、近期叙事和摘要，不能把数据库原文或完整状态投影直接塞给模型。材料的定义和来源见《记忆与上下文材料规格》；材料的收集、过滤、预算和 Agent 视图见《上下文编排规格》。

运行时只保留三条硬约束：Actor 只接收经过角色权限过滤的材料；摘要必须声明覆盖到哪个 Turn；最终上下文必须经过预算裁剪和泄漏检查。

## 5. 历史、分支与记忆

### 5.1 基础资源与故事事实分离

- 角色卡、世界书等基础资源按版本引用。被所有分支使用的“同一份卡片”不代表自动追随最新修改。
- 故事内关系、位置、已知秘密和经历均受分支历史限制。
- 用户修改基础资源时，应选择更新资源库、仅当前分支采用新版本，或明确传播到其他分支。禁止静默改写旧分支。
- 世界书条目不默认等于所有角色知道的事实；作者备注、未来剧情和秘密需要单独处理。

### 5.2 分叉规则

```text
A: E1 -> E2 -> E3 -> E4 -> E5
               |
B:             +-> B1 -> B2
```

B 能继承 A 的 `E1..E3`，不能读取 `E4/E5`，即使 A 后来继续推进也一样。

```ts
interface BranchBase {
  parentBranchId: string;
  forkCheckpointId: string;
  parentSequenceInclusive: number;
}
```

- 多层分叉对每一层祖先应用自己的截止位置，不能简单查询“所有祖先分支的全部记忆”。
- MVP 只允许从已提交 Turn 的检查点分叉；从 Turn 内消息中间分叉需要先通过“采纳完整前缀”形成独立的完整 Turn。
- 分支可以共享不可变历史与资源；后续剧情、记忆、角色知识和插件状态使用分支自己的增量。
- 不提供自动分支合并。将别的分支内容带入当前分支，必须作为明确导入或作者修正，不视为角色天然拥有跨时间线记忆。

### 5.3 角色记忆来源与检索资格

角色记忆的字段、来源、状态和检索资格见《记忆与上下文材料规格》。运行时只规定：`MemoryRecord` 不保存共享事实，必须绑定一个角色；检索先检查分支可达性和角色权限，再进行相关性排序和预算选择；其他角色记忆不能交给 Actor 或不具备权限的重排模型。

跨过分叉点的整段摘要不能直接继承。比如 A 的摘要覆盖 `E1..E5`，B 即使与 A 共享前三个事件也不能使用；需使用截至 E3 的旧摘要、重新生成摘要或回退至原始事件。

### 5.4 编辑与失效

- 用户修改事实时产生修正记录，不让旧摘要继续与新事实并列生效。
- 修改历史事件或设定后，依赖它的记忆、摘要、索引与缓存标记失效，之后按需重建。
- 摘要必须携带来源范围和读取版本，Turn 提交时重新检查来源是否仍然有效。TurnSummary 和滚动 StorySummary 在本 Turn 内同步生成；它们失败时本 Turn 不提交。
- 失效判定属于具体分支的历史视图。子分支的事实修正不能全局撤销父分支或兄弟分支仍有效的记忆；父分支分叉点之后的修正也不追溯改变既有子分支。
- 无法定位来源的导入资料不能自动变成当前分支事件，也不能自动写入任何角色记忆；用户必须明确选择来源和所属角色。
- 内置记忆检索不可用时，可回退到合格的近期 Turn、公共场景状态和角色基础资料；不能回退到全故事不加过滤的检索。

## 6. 用户可见性与角色知识隔离

### 6.1 三种不同的访问身份

| 身份 | 访问原则 |
| --- | --- |
| 故事所有者/用户 | 可查看和修改自己故事中的全部叙事状态，包括角色秘密和插件叙事状态 |
| Director / Chronicler | 可按获准能力访问完整的当前分支叙事信息，但仍不能读到不属于该分支的未来 |
| Actor | 只获得角色定义中允许的内容、其自身状态、可知事件及当前可观察信息 |

用户拥有叙事状态修改权，不意味着需要允许破坏存储主键、绕过 schema 或读取模型供应商内部信息；凭据与执行系统配置也不属于角色状态。

### 6.2 知识必须有来源

至少区分：亲身经历、现场观察、他人告知、设定中的既有知识、推断和误解。事实为真不代表每个角色知道；角色相信的内容也不一定为真。

台词的听众、动作的可观察者、私下交流和内心活动应能单独标注。在场不能自动代表能听见每句私语；读到小说旁白的用户不自动将其中信息传给角色。

“Bob 说门已经打开”首先证明 Bob 说过这句话，不直接证明门已打开。Chronicler 必须区分对话陈述、实际动作、角色观察和客观结果；未核实陈述可进入听者信念，不应自动覆盖世界事实。

### 6.3 导演也可能泄露知识

知识过滤不能只放在记忆检索处。Actor 的以下入口都要遵守同一知识视图：

- 导演下发的表演指令与局部计划。
- 角色卡/世界书的相关片段。
- 最近历史、摘要、工具结果与其他角色输出。
- 插件提供的上下文及复用的 Actor 会话状态。

例如，Director 知道 Alice 藏有钥匙，但不能向不知情的 Bob 下发“因为 Alice 偷了钥匙，所以质问她”。可以下发基于 Bob 已观察内容的目标：“询问钥匙下落，表现焦虑”。

完整导演计划必须与每个 Actor 的 `ActorBrief` 分离；后者只引用角色可访问的证据。全知计划不直接拼入 Actor prompt，其他角色私有会话也不直接共享。

对任意自然语言指令，schema 校验不能证明绝对不泄密。默认策略需结合受限数据入口、指令来源追踪、泄漏测试与必要的语义校验。已被全知插件自由编写的指令不能仅靠一个权限标签视为安全。

### 6.4 用户修改规则

用户可修改事实和角色知识，但这两个操作必须区分。例如“钥匙现在在 Bob 身上”不等于“Alice 知道钥匙在 Bob 身上”。修改面板应允许明确选择是否同步指定角色的知识。

所有核心和插件叙事状态均须有可读取表示和合法更新接口；复杂领域 UI 可由插件提供，核心提供基础结构化编辑。执行过程中编辑状态，建议先停止当前 Turn；旧版本生成结果不得继续自动提交。

## 7. 场景循环与三类 Agent

### 7.1 基本执行路径

```text
用户输入或显式继续
  -> 固定分支 head、模式、权限、资源与插件配置
  -> Director 生成有限计划
  -> 为下一个 Beat 构建角色专属输入
  -> Actor 生成台词/行动与状态提案
  -> 接受 Beat 到本 Turn 的临时工作状态，供后续 Beat 使用
  -> 有新冲突/变化：重新规划；否则执行原计划下一拍
  -> 计划完成、需用户决定或达到硬上限：结束 Beat 生成并进入 Turn 整理
  -> Chronicler 整理事件、公共状态、角色记忆和摘要
  -> 一次性提交 Turn，更新 Branch head
```

默认不要求单独模型调用完成每个框。检索、规则校验和提交可以是普通代码。Loop 表示可继续执行的调度能力，不等于强制每一步都使用 ReAct，也不要求展示模型内部推理。

用户输入始终先保存为输入记录及 `InputAttribution`。角色内台词可形成对应用户角色的发言事件；行动输入应区别意图和结果，例如“我试着开锁”不能预先写成“锁已打开”。一个 Turn 最多保存一个 `AuthorDirectiveInput`，按其明确要求形成约束或修正，而不是伪装成现场发言。用户输入引起的提交使用独立幂等键，重试模型不重复执行这些变化。

### 7.2 Director

Director 输出参与角色、计划顺序、角色目标、动作/情绪指导、依赖条件、重规划信号和结束条件。

```ts
interface ScenePlan {
  id: string;
  basedOnCheckpointId: string;
  participantIds: string[];
  beats: PlannedBeat[];
  replanTriggers: string[];
  completionConditions: string[];
}

interface PlannedBeat {
  id: string;
  actorId: string;
  dependsOnBeatIds: string[];
  briefId: string;
  preconditions: Condition[];
  maxMessages: number;
}
```

- 同一 actorId 可连续出现；一个 Beat 也可产生同一角色的多条消息。
- Director 规划时必须读取固定版本的 `ActorControlAssignment`；不得为 `controller: user` 的角色创建自动生成 Beat。控制版本变化属于 `plan_invalidated` 条件。
- 不必一次调用对应一个气泡。消息分段是表现单位，Beat 是 Turn 内的执行单位，模型请求是执行单位，Turn 是 Branch 正式提交单位。
- Scene 由 Director 根据剧情状态提出创建、结束或切换建议。Runtime 检查 Branch、状态版本、参与者和权限后，才将 SceneMutation 写入正式状态；模型不能直接写 Scene 表。
- 地点变化本身不自动创建新 Scene。只有 Director 明确提出并通过 Runtime 校验，或用户手动要求切换时，才会结束旧 Scene 或创建新 Scene。
- 存在回应依赖的 Beat 按序执行，后一个 Actor 读取前一个 Beat 已接受到本 Turn 工作状态、且对自己可见的内容；这些内容尚未成为跨 Turn 的正式事实。
- MVP 不并行提交有因果依赖的角色输出。后续可并行准备独立候选，但提交前必须校验读取版本。
- 用户被问到必须回答的问题、计划前提失效、工具结果改变场景、角色引入重大新事件等情况可触发重规划或交回用户。
- Runtime 校验所有输出的结构、授权和版本；这不等于 Director 逐句审核。

### 7.3 Actor

Actor 输入为角色身份、角色可知状态、局部导演指令及允许使用的能力。用户角色在被系统代写时也适用同一输入边界；输出为叙事表现和状态提案，不直接操作数据库。

```ts
interface ActorResult {
  beatId: string;
  actorId: string;
  segments: NarrativeSegment[];
  proposedMutations: StateMutation[];
  signals: Array<"needs_user" | "plan_invalidated" | "continue" | "done">;
}

interface NarrativeSegment {
  id: string;
  kind: "dialogue" | "action" | "emotion" | "inner_state" | "narration";
  performerId?: string;
  text: string;
  observerIds: string[];
}
```

`observerIds` 是需要按场景规则校验的提案，不能由 Actor 任意扩大。情绪的外在表现与内心事实应区别表达。

从角色卡/世界书中识别出的已有角色可以自动加入可用角色集合，并由 Director 判断是否安排登场。叙述中提及某人不等于其已经登场。

文本中发现、但没有对应 `ActorInstance` 的新角色时，Runtime 创建一个“登场候选”，由 Director 提议是否在当前 Turn 登场，并要求用户确认。用户拒绝后，只记录为当前 Turn 的拒绝决定：

- 该候选不得在当前 Turn 的后续 Plan 中登场。
- 不自动创建 Scene 级或 Branch 级的永久禁止规则。
- 下一 Turn 可以重新提议；如果用户希望长期禁止，应使用明确的作者指令或状态编辑。
- 用户确认后，Runtime 才创建或激活对应 ActorInstance，并允许 Director 将其加入后续 Beat。

候选必须保留源文本、别名、提议 Turn 和用户决定，避免每轮重复识别或身份漂移。

### 7.3.1 重大决定判断

AI 可以提出“是否属于重大决定”的分类，但不能单独决定是否放行。Runtime 使用“模型分类 + 硬规则拦截”的方式：

1. Actor 或 Director 标记候选行为的影响类型。
2. Runtime 检查是否涉及用户角色决定、不可逆结果、秘密公开、关系重大变化、分支方向变化或高风险行为。
3. 只要命中硬规则，或者模型判断不确定，就暂停并请求用户确认。
4. 只有明确不命中硬规则且模型置信度达到配置阈值时，才允许自动继续。

MVP 不追求用一个分数精确衡量“重大”。系统宁可多问一次，也不能让模型仅凭自然语言判断替用户做不可逆决定。

### 7.4 Chronicler

Chronicler 只整理 Turn 内已接受且完整的内容，不把导演计划、废弃候选、未执行工具意图和残缺句子当成已发生事实。

Chronicler 只在 Turn 结束或用户采纳完整前缀时调用。它一次性生成正式事件、公共状态、角色记忆、TurnSummary 和滚动 StorySummary；摘要是 Turn 正式提交的必需内容。Beat 结束后不单独调用 Chronicler，也不生成跨 Turn 有效的记忆。

Actor 输出只进入当前 Turn 的临时工作状态。后续 Actor 读取当前 Turn 中此前已经接受、且按观察规则可见的 Beat；不依赖 Beat 后单独生成的正式记忆。Turn 结束时才由 Chronicler 统一整理。

Chronicler 的输出必须携带来源事件和基准状态版本。它是记录者，不是可在汇总中偷偷创作新剧情的作者。多份提案冲突应显式报错或按声明规则合并，不采用无提示的最后写入覆盖。

用户取消后不自动把残缺内容交给 Chronicler。已接受的完整 Beat 仍保留在 Turn 临时状态中，等待用户选择继续完成、采纳完整前缀或完整回退；只有 Turn 正式提交后，事件、公共状态和角色记忆才成为 Branch 的有效结果。模式切换本身也不强制触发额外模型调用。

## 8. 事件、检查点与提交

### 8.1 执行日志和正式叙事分离

| 类别 | 例子 | 是否可直接成为记忆来源 |
| --- | --- | --- |
| 执行记录 | 请求开始、流式片段、导演计划、调用错误、取消信号 | 否 |
| 叙事记录 | Turn 正式提交的台词/动作、明确观察、用户事实修正 | 是，仍受知识过滤 |
| 派生记录 | 摘要生成、索引更新、状态投影完成 | 必须追溯原始来源 |

运行时事件至少包括 `turn.started`、`plan.created`、`request.started`、`request.failed`、`beat.draft_updated`、`beat.accepted`、`turn.committed`、`state.corrected`、`memory.materialized`、`turn.interrupted` 和 `turn.failed`。

事件应含 ID、Story/Branch、Turn/Attempt、因果引用、操作者、schema 版本及记录时间。正式叙事事件还需分支内顺序。系统时间与故事内时间分开存储。

### 8.2 提交单位

Turn 是 Branch 正式事实、公共状态和角色记忆的最小提交单位。Beat 只在 Turn 内被接受到临时工作状态，供后续 Beat 和实时展示使用；`beat.accepted` 不推进 Branch head，也不产生跨 Turn 有效的角色记忆。

一次短事务原子提交：

1. 本 Turn 的正式叙事事件与正文/媒体引用。
2. 公共场景状态和核心状态投影。
3. 每个角色独立的 `MemoryRecord` 变更。
4. Turn 状态、Branch head 和检查点引用。
5. 摘要、全文索引等后续任务的持久化队列记录。

模型请求、检索和生图等耗时操作位于数据库事务之外。提交使用预期 head/状态版本以及幂等键；重复提交不能重复产生台词、状态变化或记忆。

取消与 Turn 提交通过同一分支的提交闸门确定先后：Turn 先提交则保留，取消先登记则拒绝旧执行的最终提交。客户端收到最后一个 token 不代表 Beat 或 Turn 已提交。

状态变更提案至少表达以下契约：

```ts
interface StateMutation {
  id: string;
  branchId: string;
  namespace: string;
  targetId: string;
  operation: string;
  payload: unknown;
  expectedStateVersion: number;
  sourceEventIds: string[];
}
```

`operation` 与 `payload` 由版本化 schema 校验。宿主从执行身份取得权限，不信任提案自报的权限或分支。模型提案必须有有效来源；用户直接修正则关联对应的用户操作事件。同一 Turn 内的临时 Beat 可以相互引用临时状态；正式事件、状态和角色记忆必须在 Turn 提交事务内相互引用。

Chronicler 失败时保留 Turn 临时输出和“整理未完成”状态，不提交正式事件、公共状态或角色记忆。依赖该 Branch 的后续 Turn 被阻塞，直到恢复整理、采纳完整前缀或完整回退。

### 8.3 检查点

检查点至少引用叙事位置、状态投影水位、资源版本、角色知识视图版本和插件状态版本。它可以指向增量数据，不要求复制完整数据库。

检查点存在不代表所有派生任务均完成。恢复或分叉必须检查投影水位；不完整时仅使用截至该点的有效事件补齐必需状态，不能读取当前父分支的最新投影冒充历史状态。缓存键至少绑定分支/检查点、角色知识视图与资源版本。

事件回放重建的是已记录结果，不重新调用模型、网络工具或生图服务。“重新生成”是新的 Attempt，不承诺与旧输出一致。

## 9. 失败、取消、断流与重试

### 9.1 状态语义

```text
TurnAttempt: queued -> running -> completing -> completed
                         |-> interrupted
                         |-> failed

Beat: planned -> generating -> accepted
                    |-> incomplete
                    |-> failed
```

执行限制：

- 一个 Turn 最多安排 20 次模型请求。Director、Actor、Chronicler、Archivist、结构化输出修复和自动重试都计入同一个上限。Runtime 必须为 Turn 结束时的 Chronicler 至少保留 1 个请求名额；没有可用名额时，不再开始新的生成请求。
- 一个 Beat 默认生成一条消息，整个 Turn 最多生成 10 个 Beat。达到上限后进入 `needs_continue`，不自动生成第 11 个 Beat。
- 单次模型请求在 20 秒内完全没有收到任何输出时，Runtime 认为请求超时。
- 无输出超时最多自动重试 5 次；重试使用同一 `ContextSnapshot` 和请求参数，不重复提交故事状态。5 次是该请求的自动重试上限，不代表可以突破 Turn 的 20 次总上限。
- 重试请求计入 20 次安全上限，但不计入本产品的费用统计和剧情请求预算。供应商是否对已发出的 HTTP 请求收费，Runtime 无法替供应商保证。
- 已经收到部分输出后发生断流，不自动按“无输出超时”重试；进入中断或续写流程，由用户选择继续、采纳前缀或回退。

TurnAttempt 的模型执行结束不代表 Turn 已提交。只有 Chronicler 整理成功并通过 Turn 提交闸门后，Turn 才进入 `completed`，Branch head 才前进。

### 9.2 中断处理

- 用户点停止后，Runtime 发送取消信号，停止安排新的模型/工具调用，并让执行租约失效。
- 最后一个 Beat 未完整结束时，保留其文本为 `incomplete` 草稿；用户看见过不等于它已进入正式剧情。
- 已接受的完整 Beat 仍属于当前 Turn 临时前缀，不会单独推进 Branch head。后续 Actor 可以读取它的临时状态，但其他 Turn 和长期记忆不能读取。
- 用户可明确采纳完整前缀为正式剧情；Runtime 必须先确认前缀边界完整，再补做 Chronicler 整理，作为一个完整 Turn 提交。
- 用户选择完整回退时，删除或标记本 Turn 的临时状态和草稿，Branch 恢复到 Turn 开始前的检查点。
- 取消后的迟到响应可留作执行记录，但不能自动继续演出或提交状态。
- 不能保证远端请求立即停止或停止计费；本地取消不等于撤销外部副作用。

### 9.3 重试粒度

| 用户操作 | 建议语义 |
| --- | --- |
| 重试失败请求 | 在依赖和输入版本未变时，新建请求 Attempt，沿用原输入快照；不重复提交已接受 Beat |
| 接着写残缺输出 | 发起新的续写请求，显式传入草稿；不是恢复同一个远端请求，也不承诺逐 token 无缝续传 |
| 重做某个已接受 Beat | 在当前 Turn 内丢弃该 Beat 及其后续临时前缀并重新生成；若 Turn 已正式提交，则从其之前的检查点创建替代分支 |
| 重做整轮用户输入 | 从该 Turn 前的检查点执行新的 TurnAttempt；已有正式输出时建议自动创建替代分支 |
| 从当前位置继续 | 保留当前 Turn 的临时前缀，先补齐必需状态，再继续有效计划或重新规划；不得把临时前缀误当成旧 Branch head |

工具与媒体任务采用独立幂等键。外部服务不支持幂等且结果未知时，应核对任务状态或请用户选择，不能盲目重试造成重复调用。

### 9.4 并发与用户编辑

MVP 每个分支只允许一个活动执行租约。新用户输入到来时提供“停止并发送”或排队语义，不让两个 Turn 同时写同一 head。

用户当前状态修正会增加状态版本并使旧计划失效；修改历史建议在修改点创建新分支。这样保留所有修改权，同时不宣称后续既有剧情会自动正确适配新历史。

## 10. 插件与三角色替换契约

### 10.1 扩展方式

- Decorator：增强角色输入/输出，声明顺序及读写能力。
- Role Provider：替换 Director、Actor 或 Chronicler 的实现。
- Workflow Provider：替换场景工作流，仍使用宿主执行与提交接口。
- Capability Provider：注册模型、记忆、上下文编排、媒体、工具或 UI 能力。

用户显式选择某槽位的实现。单一角色槽位不能仅因插件自报更高优先级就被静默抢占。多个 Decorator 应有确定顺序和冲突检查。

```ts
interface RoleProvider<I, O> {
  id: string;
  role: "director" | "actor" | "chronicler";
  apiVersion: string;
  run(input: I, host: ScopedHost, signal: AbortSignal): Promise<O>;
}

interface ScopedHost {
  readState(query: StateQuery): Promise<StateView>;
  retrieveMemory(query: MemoryQuery): Promise<MemoryHit[]>;
  callModel(request: ModelCall): Promise<ModelResult>;
  callTool(request: ToolCall): Promise<ToolResult>;
  emitDraft(event: DraftEvent): Promise<void>;
  proposeState(mutations: StateMutation[]): Promise<ProposalReceipt>;
}
```

这些是语义接口，不固定流式 SDK 形式。`ScopedHost` 的访问范围由宿主绑定到角色和执行快照，插件不能通过传入别的 actorId 自动扩大权限。

### 10.2 可替换与不可绕过的边界

插件可以接管上下文收集、排序、预算策略和具体编译结果；不能把扩展能力限制为仅向默认编译器追加节点。

但无论使用谁的工作流，默认都必须遵守：用户授权、角色知识范围、分支隔离、状态版本校验、取消信号、总预算、事件追踪和提交幂等。

高权限导演插件本身可以读取更多资料，但给 Actor 的输出仍必须经过受限交付接口。获得明文后恶意编码泄漏的插件无法仅靠协议绝对防止，因此需要区分可信插件与受限插件，不能将 Hook API 宣称为安全沙箱。

本项目的首个发布目标是自托管，不是集中式插件托管平台。本机用户安装的后端 Node 插件属于可信服务器代码：其运行进程可能访问运行该服务的操作系统权限范围，Host API 和子进程只提供良性插件的契约、崩溃隔离、超时和可观测性，**不构成对恶意 Node 代码的安全隔离**。安装界面和文档必须明确这一点。

### 10.3 插件状态

- 使用插件命名空间与版本化 schema；同样受 Branch/Checkpoint 限制，禁止通过全局缓存串线。
- 用户有读取、修改、导出入口。插件可提供专用 UI；基础编辑器仍可访问其声明的叙事状态。
- 修改核心字段通过受控 mutation，不直接写数据库；跨插件字段写入需要显式契约。
- 插件卸载后保留数据并标为不可用，不自动删除；升级需要声明迁移与兼容方案。
- 缺少当前工作流依赖的插件时，暂停并要求选择替代，不能悄悄换实现继续故事。

### 10.4 稳定性与权限

Manifest 至少声明插件 ID、版本、宿主 API 版本、能力、权限、依赖、状态 schema 和迁移信息。执行记录固定插件版本及非敏感配置引用，不复制密钥进日志。

首版后端插件采用 Node ESM 模块，并由 `PluginHost` 以**每插件一个独立 Node 子进程**的方式运行。SDK 只提供 Host API，不提供数据库连接、主应用内部对象或模型凭据；正常插件必须通过 `proposeState`、`callModel` 等接口工作。由于插件进程仍以服务账户身份运行，恶意代码可绕开 SDK 直接访问可见文件和网络，权限 Manifest 在首版中是可见性与良性约束，不是强制安全边界。

宿主保存模型凭据，按授权代理调用；插件的网络、文件、外部服务和 UI 权限另行声明。执行超时、循环上限和取消约束由宿主控制。未来若支持不受信任的插件市场，必须引入独立的 OS/容器级隔离、只读文件系统、网络出口限制和资源配额；该能力不属于 MVP。

## 11. 展示、正文与媒体

叙事事件表达“发生了什么”，Artifact 表达“如何展示”。渲染器可以按配置隐藏、重排布局，但不得通过切换显示模式改写叙事。

- 多个气泡关联明确的说话人、顺序、Beat 和提交状态。
- 原生小说生成应保存有文学表达的正文 Artifact，并关联对应叙事事件；不能只存几个事实字段再宣称可无损还原小说。
- 将聊天历史改写成小说属于生成新 Artifact；默认只改写表达，不把新增细节自动提交为事实。采纳新增剧情需单独操作。
- 生图插件注册工具/媒体能力，生成任务与输出携带分支、来源事件、配置和任务状态。
- 图片出现不自动证明其中所有视觉细节都成为故事事实。需要采纳的细节走状态提交流程。

## 12. 酒馆兼容与模型接入

### 12.1 兼容层

角色卡、世界书和预设作为资源导入，保留原始数据、未知扩展字段与映射报告。解析格式成功不等于复现全部运行语义。

预设作为上下文策略输入，不直接拥有数据库访问或取消 Runtime 约束的权力。兼容程度以字段/行为矩阵和测试样本声明；无法等价转换的宏、脚本、注入规则应显式提示。

MVP 的酒馆兼容分为三档：

1. **直接兼容**：角色卡 V1/V2、PNG 内嵌角色卡 JSON、角色基础字段、alternate greetings、角色级 Worldbook、独立 Worldbook、用户 Persona、Preset 的主要提示词顺序和模型参数。
2. **适配兼容**：Worldbook 关键词/正则/secondary keys/constant/selective/递归激活/scan depth/插入位置；Preset 的角色卡、Persona、历史、Author's Note、Post-History Instructions、Instruct Template、Story String 和常用宏。导入后由本系统的 ContextPolicy 表达，不直接执行原始脚本。
3. **不承诺原样运行**：任意酒馆 JavaScript、STscript、任意第三方扩展 UI、依赖酒馆内部 DOM 或运行时对象的插件。

正则后处理可以兼容，但只兼容声明式规则：输入范围、匹配正则、替换文本、flags、执行顺序和启用条件。规则必须在宿主的输出管线中经过校验，不能把任意 JavaScript 当作正则规则执行。需要自定义逻辑时，改写成后端插件，并通过受限 Host API 工作。

第三方扩展 UI 不适合直接运行原始前端代码，因为它依赖 Vue 组件、DOM、酒馆内部状态和页面生命周期。MVP 提供等价的 UI Extension API，让插件注册面板、操作按钮、状态检查器和输入区扩展；原酒馆 UI 扩展需要适配器重写，不能承诺导入后直接可用。

不在本草案承诺任意酒馆 JavaScript、插件或预设均可原样运行。现有资产缺少角色知识标记时，建议提供导入预览；未分类秘密/作者说明不能默认为全员可知。

### 12.2 模型接入

MVP 使用 Vercel AI SDK 作为模型接入层，Director、Actor、Chronicler 和辅助 Agent 只调用宿主 ModelProvider。MVP 首先验证 DeepSeek Provider，同时保留其他 Vercel AI SDK Provider 的配置入口。

模型配置包括连接地址、模型标识、凭据引用、参数和能力信息；可按角色覆写配置，默认共用一个连接。模型名称和具体 API 能力在实现时查阅官方文档并实测，不在此处硬编码。

能力探测至少覆盖流式输出、工具调用、结构化输出、结束原因和取消行为。未支持的能力不得假装可用；可以通过受校验的文本协议适配，并将修复重试计入预算。Provider 适配由 Vercel AI SDK 统一，Runtime 不直接绑定某一个供应商 SDK。SDK 层的隐式自动重试必须关闭或显式设为 0，所有重试由 Runtime 创建独立的 `ModelRequestAttempt` 并纳入 Turn 的 20 次上限。

## 13. 运行环境与自托管边界

运行时由一个 Node.js 24.x 应用实例执行，并作为唯一的 SQLite 写入者、模型凭据持有者和 Turn 调度者。具体页面、HTTP 路由和 WebSocket payload 由配套规格定义。

运行时核心使用 TypeScript，与 Web 框架、Vue 和具体 SQLite 驱动隔离；通过 Repository、ModelProvider、MemoryService、ContextCompiler 和 PluginHost 接口访问外部能力。首版实现采用 Fastify、TypeBox、Drizzle ORM 和 better-sqlite3，但领域规则不得依赖这些具体库的对象。

### 13.1 SQLite、文件和并发

默认数据目录由 `APP_DATA_DIR` 指定；Docker 默认挂载为 `/data`。该目录是应用状态，不能放在容器临时文件系统中。

```text
$APP_DATA_DIR/
  app.sqlite            SQLite database
  vector/               LanceDB tables and indexes
  media/                uploaded and generated media
  plugins/              installed plugin packages and lock metadata
  backups/              application-created backups
```

- SQLite 必须启用 WAL、外键约束和 busy timeout。所有数据库写操作只在 `apps/server` 所属主机执行，并维持第 9 节定义的 Branch 执行租约与短事务。
- 同一 `APP_DATA_DIR` 不得被多个 `app` 实例同时读写；不支持多副本部署、跨机器共享 SQLite 文件或把该目录放在网络文件系统上。
- 容器重启、升级和插件崩溃不得丢失已提交事件。Docker Compose 必须使用命名卷或宿主机持久化目录挂载 `APP_DATA_DIR`。
- 媒体文件保存在 `media/`，SQLite 只保存元数据、内容哈希、来源事件和逻辑路径；不将大媒体二进制直接写入事件表。
- 数据库迁移在服务启动阶段独占执行。迁移失败则服务不得开始接受 Turn；并发启动不是支持场景。
- 备份必须通过应用提供的 SQLite 在线备份流程或停止服务后完成的文件快照执行；运行中不得仅复制主数据库文件而忽略 WAL 状态。
- 首版不依赖 Redis、PostgreSQL 或外部任务队列；向量索引使用 `$APP_DATA_DIR/vector` 中的 LanceDB，SQLite 保存来源和权限元数据。TurnSummary 和 StorySummary 在 Turn 提交前同步生成；FTS、LanceDB 写入、媒体处理和其他可恢复后台工作使用 SQLite 任务记录。

### 13.2 凭据与访问边界

- 模型 Provider 的 API Key 仅由后端 SecretStore 读取。保存后的密钥不得再次通过 HTTP、WebSocket、事件日志、插件日志或前端状态返回明文。
- 环境变量可提供服务级默认模型凭据。用户通过 UI 配置的持久化凭据必须在后端加密存储，并要求部署者配置 `APP_SECRET_KEY`；未配置时 UI 不允许持久化新的密钥。
- 默认仅监听 `127.0.0.1`。用户可以在配置文件或启动参数中启用局域网监听；服务仍只有一个账号，不做多用户 Story 隔离。
- 系统使用普通账号密码鉴权，不使用“管理员登录”作为产品概念。MVP 从本地 `.env` 读取单用户账号和明文密码；密码不提交 Git、不写入数据库、不通过 API 返回。HTTP API 和 WebSocket 都必须完成鉴权，Session 使用 HttpOnly Cookie 或等价的服务端会话机制。该方案只适用于用户自行部署的单用户环境。
- 公网暴露不属于 MVP 的受支持部署目标；用户自行配置反向代理和公网访问时，需要自行承担 TLS、暴力破解防护和网络边界责任。

### 13.3 Node 插件的自托管信任模型

- 后端插件是 Node ESM 包，由本机用户通过本地 CLI 或管理界面安装。安装动作必须记录来源、版本、完整性信息和 Manifest 快照。
- 每个插件固定在独立 PluginHost Node 子进程内执行；宿主通过版本化 RPC 提供 Runtime 能力。进程边界用于稳定性、取消、资源统计和日志归属，不是恶意代码安全边界。
- 插件 Manifest 中的 `network`、`filesystem`、`model:call`、`state:write` 等权限必须展示给用户并写入执行日志。首版可以阻止良性插件通过 SDK 调用未获授权能力，但不能阻止恶意 Node 代码自行使用服务账户可访问的资源。
- PluginHost 不向插件传递数据库对象、原始模型密钥或 Fastify 实例。符合 SDK 的插件通过 Host API 读取状态、调用 Provider 和提交 mutation。
- 不受信任后端插件和加载任意第三方前端 JavaScript 均属于后续独立安全设计。

## 14. MVP 范围

### 14.1 第一条运行路径

1. 通过 Vercel AI SDK 手动配置 DeepSeek 或其他已接入 Provider，导入基础角色卡与世界书。
2. 创建 Story、默认 Branch、活动 Scene 和稳定的角色实例。
3. 默认 Director 一次规划多个 Beat，至少跑通 `Bob -> Bob -> Alice -> Bob`。
4. Actor 使用各自知识视图；Turn 内已接受的 Beat 可被后续角色按观察规则读取，Turn 提交前不进入跨 Turn 正式历史。
5. Turn 结束时由 Chronicler 一次性完成事件、状态、角色记忆、TurnSummary 和 StorySummary；摘要成功是 Turn 提交的必要条件。
6. 用户能停止、查看草稿、请求级重试、整轮重做并从检查点分叉。
7. 提供聊天/小说输入语义切换，共享状态；支持基础小说正文 Artifact。
8. 支持多份用户人设、Story 内多个用户控制角色，以及每条输入的明确人设归属。
9. 支持用户临时接管和显式交还 NPC；控制版本变化能使旧 Plan 失效。
10. 剧情权限与展示设置分开；提供最小状态查看/编辑入口。
11. 使用一个示例插件替换 Director 或增强 Actor，验证扩展不依赖修改宿主源码；插件 Manifest、能力注册、状态 JSON 建议结构和 Host RPC 属于 MVP 的可用边界。

### 14.2 不属于核心 MVP 的生态能力

- 任意酒馆 JavaScript、STscript 和第三方扩展 UI 的原样运行。
- 生图等媒体插件的具体实现；核心保留 Artifact 和媒体插件接口，生图插件在核心 MVP 完成后提供并可默认安装。
- 面向不可信代码的插件市场与生产级隔离。
- 自动分支合并、并行活动场景、复杂群像规划及长篇全自动写作。

核心 MVP 覆盖本文、记忆规格、上下文规格、接口规格和数据模型规格中已经写明的核心功能，包括多角色循环、分支、记忆、摘要、向量检索、Archivist、用户人设、作者指令、角色接管、单用户鉴权、插件 Host 和酒馆资产兼容适配。第 14.2 节只表示不在核心 Runtime 中实现的生态或安全能力。

运行时验收场景、示例故事和测试观察指标见《示例故事与验收标准》。本规格只要求：实现必须覆盖该文档中的核心场景，并且模型输出测试不能替代事件、分支、角色知识和提交边界的数据隔离测试。

## 16. 已确定边界与后续实现顺序

### 16.1 不属于 v0.1 的实现承诺

1. 任意酒馆 JavaScript、STscript 和依赖酒馆内部 DOM 的插件不承诺原样运行；兼容边界见《酒馆兼容矩阵》。
2. 后端 Node 插件属于自托管可信代码，v0.1 不提供恶意插件沙箱。
3. 生图插件的具体实现不属于核心 Runtime；核心只提供媒体 Artifact 和媒体 Provider 接口。
