# 记忆与上下文材料规格

- 版本：0.1
- 日期：2026-09-23
- 状态：运行时和上下文编排使用的记忆与材料规格。
- 依赖：[叙事运行时规格](./叙事运行时规格-v0.1.md)、[接口契约规格](./接口契约规格-v0.1.md)、[数据模型规格](./数据模型规格-v0.1.md)。
- 范围：事件、公开状态、角色记忆、Turn 记忆处理、摘要层级、上下文材料表示和基本检索边界。
- 非范围：具体模型提示词、插件 SDK 细节和完整 Worldbook 兼容矩阵。MVP 的向量索引使用 LanceDB；SQLite 表结构见[SQLite 持久化规格](./SQLite持久化规格-v0.1.md)；上下文视图、预算和编排流水线见[上下文编排规格](./上下文编排规格-v0.1.md)。

## 1. 核心原则

系统必须把“发生过什么”和“谁记得什么”分开保存：

```text
NarrativeEvent  真实发生或被用户明确修正的事情
PublicState     事件产生的、当前公开可观察的状态
ActorMemory     某个角色个人记得、相信、怀疑或经历的内容
```

1. `NarrativeEvent` 是故事事实来源，但不直接进入 Actor 上下文。
2. `PublicState` 不是共享记忆，只保存当前场景中角色正常观察即可知道的少量状态。
3. `ActorMemory` 永远绑定一个 `subjectActorId`，不设计共享记忆实体。
4. 一个事件可以产生一条公开状态和多条不同的角色记忆，也可以没有任何角色记忆。
5. 角色记忆可以错误、过时或不完整，但不能覆盖客观事件。
6. Turn 是正式生成角色记忆、公开状态和剧情事件的基本单位。
7. Beat 只在 Turn 内形成临时工作状态；Turn 未提交前，临时内容不能被下一个 Turn 使用。

## 2. 四类基础材料

### 2.1 世界规则

世界常识和故事设定统一归入 `WorldRule`。例如“太阳从东边升起”和“本世界太阳从西边升起”属于同一种材料，只是来源不同。

世界规则来源从低到高可以是：

```text
模型默认常识
< Story 绑定的 Worldbook
< Story 明确覆盖设定
< Branch 内已确认的规则修正
```

规则是否成立与角色是否知道规则是两件事。每条规则至少需要表达：

- 来源和版本。
- 适用的 Story、Branch 或 Scene。
- 是否对所有角色可知。
- 适用角色范围。
- 与其他规则冲突时的优先级。

一个 Story 可以绑定多本 Worldbook。每本 Worldbook 独立保存版本、优先级、条目和激活条件。上下文编排时选择适用条目，不把所有世界书一次性拼入上下文。

### 2.2 事件

事件表示已经发生的事情，或者用户明确提交的事实修正。

```ts
interface NarrativeEvent {
  id: string;
  storyId: string;
  branchId: string;
  turnId: string;
  sequence: number;
  kind: "utterance" | "action" | "observation" | "state_correction" | "rule_correction";
  actorId?: string;
  payload: unknown;
  sourceEventIds: string[];
}
```

事件必须带分支和 Turn 来源。事件一旦正式提交，不因摘要更新而改变；需要修正时追加修正事件，并让依赖旧事件的派生数据失效。

事件本身可以被 Director、Chronicler 和用户查看，但 Actor 默认只通过角色视图读取事件造成的结果。

### 2.3 公开状态

公开状态是从事件投影出的当前可观察信息，不是角色记忆。

MVP 只要求保存当前场景需要的最小公共状态：

```ts
interface PublicSceneState {
  sceneId: string;
  storyTime?: string;
  location?: string;
  presentActorIds: string[];
  visibleObjects: Array<{ id: string; label: string; state?: unknown }>;
  visibleChanges: string[];
}
```

默认可以进入每个在场 Actor 的上下文，但仍要经过观察规则过滤。例如墙后的物品、私下交谈和不可见的内心活动不能进入公共状态。

角色位置、携带物品、关系强度和未公开目标不属于公共状态，应放入角色专属状态或角色记忆。伤势在 MVP 不作为结构化状态字段处理，只有在剧情中有意义时通过事件、记忆或自然语言摘要表达。

### 2.4 角色记忆

角色记忆只保存一个角色对故事的个人认知：

```ts
interface ActorMemory {
  id: string;
  storyId: string;
  branchId: string;
  subjectActorId: string;
  sourceEventIds: string[];
  sourceTurnId: string;
  kind: "knowledge" | "belief" | "suspicion" | "experience" | "personal_summary";
  content: string;
  confidence?: number;
  status: "active" | "stale" | "revoked";
  validFromEventId?: string;
  validUntilEventId?: string;
}
```

示例：

```text
事件：Alice 把钥匙藏到书架后面。

AliceMemory：我把钥匙藏在书架后面。
BobMemory：我没有看见 Alice 藏钥匙。
CarolMemory：我听到书架附近有声音，但不知道发生了什么。
```

没有观察到事件的角色，不应因为事件存在就自动获得一条“我不知道这件事”的记忆。缺少记忆本身通常就表示角色不知道；只有剧情需要表达角色曾经思考过但判断错误时，才创建明确的误解或怀疑记录。

## 3. Turn 记忆处理

### 3.1 Turn 内部阶段

```text
Turn 开始
  -> 固定 Branch head 和执行配置
  -> Director 规划
  -> Actor 生成 Beat
  -> Beat 接受至 TurnWorkingState
  -> 后续 Beat 读取 TurnWorkingState
  -> 全部输出结束
  -> Chronicler 生成正式事件、公共状态和角色记忆提案
  -> 通过提交闸门
  -> Turn 正式提交
```

`TurnWorkingState` 只服务于当前 Turn。它可以包含已经接受的 Beat、临时事件、临时状态和角色在本 Turn 内新获得的信息，但不能被其他 Turn 或其他 Branch 读取。

### 3.2 正式提交内容

Turn 提交时需要统一处理：

1. 正式叙事事件。
2. 公共场景状态变化。
3. 角色个人状态变化。
4. 每个受影响角色的个人记忆变化。
5. TurnSummary、StorySummary 和必要的场景摘要记录。
6. Branch head 和 Turn 检查点。

任何一个必要部分无法完成时，Turn 不进入正式完成状态。可以保留临时输出和待整理任务，但不能让下一个 Turn 读取半成品状态。

### 3.3 中断处理

中断 Turn 必须进入待解决状态：

```text
interrupted_pending_resolution
```

允许三种结果：

- 继续生成并完成原 Turn。
- 采纳完整前缀，重新执行 Chronicler 并把前缀作为完整 Turn 提交。
- 完整回退到 Turn 开始前的 Branch head。

残缺句子不能直接变成正式事件。用户看到过流式草稿，也不代表角色已经经历了这段剧情。

## 4. 摘要系统

### 4.1 摘要不是记忆替代品

摘要用于压缩已经发生的长篇内容，不能替代关键事件、角色状态和角色个人记忆。

关键状态必须结构化保存，例如：

- 角色身份和当前位置。
- 角色关系。
- 物品归属和位置。
- 秘密是否已经公开。
- 世界规则是否被当前 Story 覆盖。
- 角色未完成目标。

自然语言摘要负责帮助模型理解背景，结构化状态负责保证关键事实不丢失。

### 4.2 摘要层级

```text
TurnSummary
  -> SceneSummary
  -> ArcSummary
  -> StorySummary
```

每层摘要都必须记录覆盖范围：

```ts
interface SummaryRecord {
  id: string;
  branchId: string;
  level: "turn" | "scene" | "arc" | "story";
  coveredThroughTurnId: string;
  sourceTurnIds: string[];
  content: string;
  status: "active" | "superseded" | "invalid";
}
```

Turn 正常结束时必须同步生成 `TurnSummary`，并更新当前有效的 `StorySummary` 或其滚动版本。摘要生成成功是 Turn 正式提交的必要条件。

Actor 的历史剧情材料默认使用：

```text
当前 Turn 已接受的 Beat
+ StorySummary
+ 最近已提交 Turn 的 TurnSummary
+ 当前角色相关的 ActorMemory
+ 当前适用的 WorldRule
+ 当前 PublicSceneState
```

Actor 默认不直接读取一长段前文 Turn 原文。摘要生成失败时，Turn 不正式提交；不能跳过摘要继续推进，也不能随便删除最早的故事内容。

### 4.3 摘要继续压缩

当 `StorySummary` 本身超过预算时，生成新版本：

```text
旧 StorySummary
+ 新完成的 ArcSummary
-> 新 StorySummary
```

新版本通过校验后才替换当前版本，旧版本保留用于审计和重新生成。不能直接按字符或 token 从摘要开头截断。

## 5. 上下文材料的结构化边界

### 5.1 可以结构化的内容

以下内容优先使用结构化表示：

| 内容 | 推荐表示 |
| --- | --- |
| 当前时间和地点 | 字段 |
| 在场角色 | Actor ID 数组 |
| 角色位置、物品 | 角色状态对象 |
| 物品位置和归属 | 关系或状态记录 |
| 角色关系 | 带类型和强度的关系记录 |
| 世界规则 | 带来源和优先级的规则条目 |
| 角色记忆 | 带来源、类型、状态和角色 ID 的记录 |
| 摘要覆盖范围 | Turn 游标 |
| 用户是否接管角色 | 控制状态 |
| Turn 和 Beat 状态 | 状态机枚举 |
| 工具结果和媒体 | Artifact/Tool Event 引用 |

结构化不代表把数据库 JSON 原样塞进模型。上下文编译器需要把结构化状态编译成稳定、简洁、可读的模型输入。

### 5.2 适合保留为自然语言的内容

以下内容通常保留自然语言：

- 角色说话风格、价值观和表现要求。
- 场景气氛和文学语境。
- 角色个人记忆的短文本表达。
- TurnSummary、SceneSummary、ArcSummary 和 StorySummary。
- 用户作者指令。
- Worldbook 中不能安全拆分的原始条目。

这些内容也要有来源、作用域和预算，不应无限追加。

### 5.3 Agent 视图的材料边界

三类 Agent 使用不同的上下文视图：

- `DirectorView`：用于规划当前 Branch 的剧情，可读取完整事实视图，但必须识别材料的公开性。
- `ActorView`：只包含指定角色有资格知道的角色卡、世界规则、公共状态、个人状态、个人记忆和可见叙事。
- `ChroniclerView`：包含本 Turn 已接受的完整临时输出和 Turn 开始前的正式状态，用于整理已发生内容。

Actor 不得读取其他角色的个人记忆、完整导演计划、Chronicler 内部分析或未观察到的秘密。详细的材料过滤顺序、`ContextItem`、Token 预算、`ActorBrief` 和三个 Agent 的视图规则见[上下文编排规格](./上下文编排规格-v0.1.md)。

## 6. 检索边界

MVP 包含向量索引和只读 Archivist 检索 Agent。检索必须先完成 Branch、时间范围和角色权限过滤，再在合格候选中进行关键词、全文或向量检索。上下文编排规格定义默认材料优先级和预算；本节只规定检索不能突破的边界：

1. 检索结果只能来自当前 Branch 可达的正式记录和已授权材料。
2. 角色记忆只能返回给对应的 `subjectActorId`，除非它已经通过事件或公共状态正式公开。
3. 结果必须保留来源、有效时间和分支范围。
4. SQLite 条件查询和全文检索、向量索引都只是检索手段，不能成为事实来源。
5. Archivist 只能从已过滤的候选中整理带来源的结果，不能通过向量相似度扩大权限。

Archivist 属于 MVP 的只读辅助 Agent。它只能返回带来源的候选资料，不得直接修改事件、公共状态或角色记忆。

## 7. 分支规则

- 分支从已提交 Turn 的 Checkpoint 创建。
- 子分支继承分叉点之前的事件、公共状态和各角色记忆。
- 分叉点之后产生的事件和角色记忆只属于子分支。
- 角色记忆不会因为“属于同一个 actor”而跨分支共享。
- 摘要必须按分叉点截断或重建，不能使用覆盖父分支未来内容的摘要。
- 用户在子分支中修改某个角色记忆，不影响父分支或兄弟分支。

## 8. 用户修改

用户可以分别修改：

```text
客观事实/公共状态
某个角色的个人记忆
世界规则
摘要文本
```

这些操作必须生成不同类型的修正记录。特别是：

```text
“钥匙在 Bob 身上”
不等于
“Alice 知道钥匙在 Bob 身上”
```

编辑角色记忆时必须选择所属角色和当前 Branch，并保留来源、操作者和修改时间。

## 9. MVP 验收场景

| ID | 场景 | 必须满足的结果 |
| --- | --- | --- |
| M01 | Alice 看到秘密，Bob 不在场 | 事件存在；只为 Alice 生成相关记忆 |
| M02 | Bob 听到 Alice 的公开发言 | Bob 获得对应记忆，但不自动获得 Alice 的私密事实 |
| M03 | 一个事件产生不同角色认知 | 每个 ActorMemory 独立保存，内容可以不同甚至互相矛盾 |
| M04 | 一个 Turn 产生多个 Beat | Beat 可被同 Turn 后续 Actor 读取，但 Turn 外不可读取，直到 Turn 正式提交 |
| M05 | Turn 中途断流 | 保留临时前缀，要求继续、采纳完整前缀或回退；不生成半正式记忆 |
| M06 | Turn 正常完成 | Chronicler 同步生成事件、公共状态、角色记忆、TurnSummary 和 StorySummary；全部成功后与 Branch head 一起提交 |
| M07 | 摘要覆盖旧 Turn | 近期原文不重复注入摘要已经覆盖的内容 |
| M08 | Story 绑定多本 Worldbook | 条目独立保存并按优先级和激活条件选择，不永久合并原文 |
| M09 | 长期摘要继续压缩 | 生成新版本，旧版本可审计，不直接截断摘要开头 |
| M10 | Actor 请求秘密信息 | 检索先按角色 ID 和 Branch 过滤，不能通过排序器、向量索引或 Archivist 绕过权限 |
